1. 제품 목표와 Output

삼성전자우 가격을 직접 맞히는 모델이 아니라, 가격을 만들어내는 경제·산업·기업·수급·Valuation 시스템을 지속 관측하고 가능한 미래를 확률로 설명하는 AI Future Reasoning System을 구축한다.
Horizon필수 Output
1 Day상승/하락/횡보, 장중 Risk Event, Flow/Regime 중심.
1 WeekMacro Event, 수급, 기술적 Regime, 단기 Catalyst.
1 Month금리·환율·Memory 가격·Earnings revision·외국인.
3 MonthsAI Demand, Memory supply/demand, EPS, Valuation, Policy path.

각 Horizon은 Probability 3개 합계 100%, Price Range, Model Confidence, Top Positive Drivers, Top Negative Drivers, What Would Change My Mind를 반환한다.

3. Ontology → Knowledge Graph → Neo4j 구현

3.1 Ontology는 코드와 문서로 먼저 정의

Ontology는 확률을 계산하지 않는다. 공통 의미를 고정하는 역할만 한다. 초기 v1.1에서는 OWL/RDF를 강제하지 않고 YAML/JSON Schema로 관리한 뒤 Neo4j Label/Relationship 모델로 투영한다.

ontology/
  entities.yaml
  factors.yaml
  relationships.yaml
  modules.yaml
  evidence_types.yaml
  regimes.yaml

  Company: [SamsungElectronics, SKHynix, Micron, CXMT]
  Security: [SamsungCommon, SamsungPreferred]
  MacroVariable: [US10Y, DXY, USDKRW, CPI]
  IndustryVariable: [DRAM_ASP, HBM_Demand, Inventory]
  Event: [FOMC, CPIRelease, EarningsRelease]
  Module: [Macro, Memory, Valuation, ...]

3.3 초기 Cypher 제약/인덱스

CREATE CONSTRAINT factor_id_unique IF NOT EXISTS
FOR (n:Factor) REQUIRE n.id IS UNIQUE;

CREATE CONSTRAINT module_id_unique IF NOT EXISTS
FOR (n:Module) REQUIRE n.id IS UNIQUE;

CREATE INDEX factor_name_idx IF NOT EXISTS
FOR (n:Factor) ON (n.name);

Neo4j는 schema-free/open-schema 특성을 가지므로 v1.1에서는 안정적인 id/핵심 필드만 constraint로 고정하고 Factor/Edge는 확장 가능하게 둔다.

4.2 SQL Sample

create table factor_observations (
  id bigint generated always as identity primary key,
  factor_id text not null,
  observed_at timestamptz not null,
  value numeric,
  value_json jsonb,
  source_id text,
  confidence numeric check (confidence between 0 and 1),
  created_at timestamptz default now(),
  unique(factor_id, observed_at, source_id)
);

create index factor_obs_lookup
on factor_observations(factor_id, observed_at desc);

5.3 Probability 계산 규칙 v1.1

처음부터 복잡한 Bayesian Network를 강제하지 않는다. v1.1는 설명 가능성을 우선하여 calibrated log-odds + causal contributions + historical relevance adjustment로 시작하고, 실제 Forward Test가 쌓이면 Bayesian Network/structural causal model로 교체 가능하게 한다.

1. Horizon별 prior 산출
2. 최신 Module State → evidence likelihood 변환
3. Causal Graph로 중복/상쇄/lag 적용
4. Historical Experience는 relevance gate 통과분만 적용
5. Challenger penalty 적용
6. up/down/flat normalize
7. calibration layer 적용
8. 모든 delta를 forecast_contributions에 저장

21-6. 구현 원칙

  • Engine 사이에는 자유형 LLM 텍스트가 아니라 Typed Artifact만 전달한다.
  • LLM의 숨은 사고과정을 저장하는 것이 아니라 SituationState, Hypothesis, CausalPath, ChallengeReport 등 검증 가능한 구조화 결과를 저장한다.
  • Neo4j는 관계·인과경로·Graph Version, Supabase는 시간·상태·Forecast·Journal·Review를 담당한다.
  • Decision Policy는 E18 이후에만 적용하여 ENTRY/SELL 목표가 Forecast를 오염시키지 않게 한다.
  • E19가 실패하면 Forecast를 내보내지 않고 오류가 난 Engine을 지정해 Retry한다.
  • 모든 Run은 data cutoff, ontology version, graph version, model version, prompt version을 고정해 재현 가능해야 한다.

22. v1.1 Decision Architecture — Future Reasoning × Price Wave × Multi-Timeframe

v1.1의 핵심 원칙은 매수·매도를 기술적 분석만으로 결정하지 않는 것이다. 19개 Future Reasoning Engine이 방향과 확률을 판단하고, Price Wave/Reversal Engine이 해당 Horizon에서 진입·이탈 시점을 판단하며, Multi-Timeframe Alignment와 Liquidity Confirmation이 구조적 정렬을 확인한 뒤 Decision Engine이 최종 Action을 결정한다. 기술적 신호는 다시 Market Regime, Capital Flow, Reflexivity 관련 Reasoning으로 피드백되어 Future Reasoning을 재계산할 수 있다.

22-3. Bottom Reversal Logic

하락파동 → 과매도 → 1차 저점 → 반등 → 2차 저점 → 가격 저점 유지 또는 higher low → RSI bullish divergence → 매도거래량 감소 → 변동성 수축 → neckline 돌파 → Fast/Medium/Slow Trend 회복 → 외국인/기관/거래량 확인 → Bottom Reversal Confirmed의 순서로 판단한다.

단기에서는 30분봉, 중기에서는 일봉, 장기에서는 주봉에서 같은 논리를 적용한다. 20/60/120 period는 초기 실험값이며 절대규칙이 아니다.

22-4. Top Reversal Logic

상승파동 → 과매수 → 1차 고점 → 조정 → 2차 고점 → lower high 또는 RSI bearish divergence → 매수거래량 둔화 → 변동성 확대 → neckline 하향이탈 → Fast/Medium/Slow Trend 이탈 → 외국인/기관 수급 악화 → Top Reversal Confirmed의 순서로 판단한다.

22-8. Feedback Loop

Wave Engine은 후처리만 하는 것이 아니다. 쌍바닥, 거래량 확장, 외국인 수급 전환, 추세선 회복은 Market Regime·Capital Flow·Reflexivity의 새로운 Evidence가 된다. 따라서 기술적 신호 발생 시 관련 Reasoning Engine을 재실행할 수 있다.

예: 30분봉 Bottom Reversal + 외국인 순매수 전환 → Capital Flow State 개선 → Market Regime State 개선 → Actor/Reflexivity 경로 강화 → Future Upside Probability 재계산 → Decision Engine 재평가.

22-9. Position-aware Multi-Horizon Management

단기, 중기, 장기 Signal이 서로 달라도 정상이다. 단기 SELL과 장기 HOLD/ENTRY가 동시에 발생할 수 있으며 Horizon별 Position State를 별도로 관리할 수 있어야 한다.
